## 1. Root-cause analysis

The supplied application has three independent authorization failures and one file-system access vulnerability.

The primary problem is that the endpoints perform operations without establishing the identity and permissions of the requester.

In particular:

1. `GET /students/<student_id>/profile` has no authentication or record-level authorization.
2. `GET /grades/<student_id>` returns grades without checking the requester's permissions.
3. `POST /grades/update` modifies or creates grades without authentication or role/course authorization.
4. `GET /files` passes a user-controlled path directly to `flask.send_file()`, allowing directory traversal and symlink escapes.

There is also an important session-security consideration: authorization should resolve the authenticated username against the server-side `USERS` database rather than trusting the role, student ID, or course assignments stored in the session.

Recommended approach: introduce a small shared authentication helper, enforce authorization before processing protected requests, and apply filesystem containment checks before serving files.

The patch should preserve grade creation for authorized users, as well as the existing successful update response.

## 3. Explanation of the controls

### A. Centralized authentication

`authenticated_user()` resolves the session username against `USERS`.

This is important because the existing implementation stores role, student ID and course assignments in the session. Those session attributes should not be treated as the authoritative source of permissions.

The `login_required` decorator provides a common authentication check.



401

&#x20;No authenticated user.





403

&#x20;Authenticated user without the required permission.



The decorator also ensures that an unauthenticated malformed grade-update request receives 401 before JSON parsing can fail.

### B. Grade-update authorization

The authorization rules are:

| User                         | Update existing grade | Create missing grade |
| ---------------------------- | --------------------- | -------------------- |
| Unauthenticated              | 401                   | 401                  |
| Student                      | 403                   | 403                  |
| Professor assigned to course | 200                   | 200                  |
| Professor not assigned       | 403                   | 403                  |
| Administrator                | 200                   | 200                  |

The authorization check occurs before `find_grade()` and before either modifying or appending to `GRADES`.

Crucially, the existing creation branch remains intact:

```
if row is None:    GRADES.append({        "student_id": student_id,        "course_id": course_id,        "grade": grade    })else:    row["grade"] = grade
```

This preserves the legitimate create-record functionality.

### C. Grade-list authorization

The endpoint filters records according to the authenticated user's permissions:

- Students: their own records.
- Professors: records belonging to their assigned courses.
- Administrators: all records.

Unauthorized records are never included in the response.

The patch returns 403 when the resulting permitted record collection is empty, as required by the stated authorization rule.

### D. Profile authorization

The endpoint requires authentication.

- Administrators can read student profiles.
- Students can read their own profiles.
- Professors cannot read student profiles.

The student-own-profile restriction is an explicit least-privilege assumption because the requirements do not specify whether students may read other students' profiles.

### E. File-download protection

The file endpoint now:

1. Requires authentication.
2. Decodes URL-encoded paths.
3. Rejects absolute paths.
4. Resolves the requested path against the canonical materials directory.
5. Checks containment using `Path.relative_to()`.
6. Rejects missing files, directories and symlinks resolving outside the permitted directory.

This is stronger than a simple string-prefix check, which would incorrectly accept sibling directories sharing the same textual prefix.

All protected paths that need consistent controls are:

| Endpoint                     | Authentication    | Additional authorization              |
| ---------------------------- | ----------------- | ------------------------------------- |
| `GET /`                      | Public            | None                                  |
| `POST /login`                | Public            | Credential verification               |
| `POST /logout`               | Existing behavior | None                                  |
| `GET /me`                    | Optional          | Returns null when anonymous           |
| `GET /students/<id>/profile` | Required          | Own profile or admin                  |
| `GET /grades/<id>`           | Required          | Own grades, assigned courses or admin |
| `POST /grades/update`        | Required          | Assigned professor or admin           |
| `GET /files`                 | Required          | Resolved filesystem containment       |

This inventory prevents fixing only the failing update endpoint while leaving equivalent access-control vulnerabilities elsewhere.

## 5. Remaining assumptions and limitations

There are several points worth addressing before considering the application production-ready.

1\. Flask session signing key

The original application contains:

```
app.config["SECRET_KEY"] = "dev-secret-key"
```

This is unsuitable for production. A known signing key allows attackers to forge Flask session cookies.

Replace it with a securely generated secret supplied through deployment configuration. The patch's server-side user lookup does not compensate for a compromised session-signing key.

2\. Student grade visibility

The requirements explicitly define professor and administrator access, but do not fully specify student grade visibility. The patch assumes students can read only their own grades.

3\. Empty grade results

The patch interprets the requirement to deny requests with no permitted records literally, returning 403 rather than an empty array.

4\. Filesystem race conditions

Canonical path resolution protects against ordinary traversal and symlink attacks. However, a highly concurrent attacker able to modify the materials directory between validation and file opening could create a time-of-check/time-of-use race. A production implementation should use safer descriptor-based file opening and appropriate filesystem permissions.

5\. Grade validation

The patch preserves the existing grade representation and response format. It does not introduce a new grading scale or range restriction because neither is specified.
